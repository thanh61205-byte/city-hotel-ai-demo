# G2 tool choice justification (PDMT: Tools)

| Tool | Role | Scalability | Collaboration | Usability for non-technical managers |
|---|---|---|---|---|
| Python (pandas, scikit-learn, XGBoost) | F v3.1: weekly scoring, tiers, rules, dated schedule; G1 (notebook 05): policy and capacity-limited schedule; `dashboard/data_contract.py` checks and loads both for G2 | Weekly batch of new bookings (12,102 individual + 1,054 group bookings in 2017); scheduling needs engineering | Reproducible notebooks, `run_id` + code / input hashes in manifests | Invisible to the manager; outputs reach staff through the dashboard |
| PostgreSQL 16 | (1) the `hotel` data model (`sql/schema.sql`, 10 tables + 2 views, `sql/verify_load.sql` 30/30); (2) the shared G2 action store via `G2_DB_URL` (one schema per F run + G1 policy, `dashboard/pg_backend.py`) | Indexes, constraints, multi-user access; writes serialised per store, lock wait bounded at 15 s | Shared structured tables and reviewable, generated SQL (`sql/g2_state_store_postgres.sql`) | Never requires the manager to write SQL |
| SQLite (local demo store) | Same action store on one laptop (default when `G2_DB_URL` is not set), same CHECKs, triggers and messages | One writer at a time; not meant as the shared multi-user store | Not shared automatically; one file per F run + G1 policy + store version | No database configuration needed for the first demo |
| Streamlit (G2 UI) | Booking review dashboard: today's work list, weekly queue, booking explorer, action schedule, cancellation buffer, actions and approval, KPIs | Fast proof of concept; one connection per browser session; needs a different deployment (and login) at high traffic | Python code versioned with the rest of the project | Filters, tables and buttons; no coding for managers |
| n8n 2.x | Visual workflow prototype: webhook → approval / execution guard → mock dispatch → response (sends nothing) | Can add workers / queues when deployed appropriately; production flow designed in `docs/G2_architecture.md` | Transparent nodes for analytics / operations review; node code in `n8n/src/` | Staff can follow a sequence of triggered actions |
| GitHub | Source versioning / review | Works across project revisions | Pull requests, history and review | Managers consume demos, not GitHub code |
| unittest + Node.js | Tests for data contract, approval guard (SQLite and PostgreSQL), concurrency, n8n node code, live webhook and app rendering | Runs in about a minute on any laptop | Same tests for every member before merging | Not used by managers |

**Decision:** Streamlit + SQLite give a beginner-friendly standalone G2 demo; setting `G2_DB_URL` keeps the same store in PostgreSQL with the same rules (store tests pass on PostgreSQL 16). The `hotel` data model stays the group's authoritative schema; its approval-guard migration is `sql/g2_approval_guard_postgres.sql`. n8n remains a demo workflow: no guest is contacted and no PMS, price or inventory is changed.

**Minimum required by brief:** justify tool choices and explain workflow. G2 also provides a working demonstration (partial implementation). Real channels, a scheduled n8n flow reading PostgreSQL and authentication are production steps, not part of the prototype.
